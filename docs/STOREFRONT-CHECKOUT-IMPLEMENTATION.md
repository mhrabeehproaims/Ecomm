## Checkout and inventory workflow

- Prices use the selected catalog price and current active offer value. All money is calculated in integer paise with the already-installed Brick Math library for overflow-safe proportional calculations; no new dependency was added.
- Coupon eligibility uses the real offer-adjusted product subtotal. Discounts are capped at the subtotal and allocated cumulatively so item shares add up exactly. Pending reservations count toward coupon limits; cancellation/expiry releases those reservations, while committed uses remain recorded.
- Catalog prices remain tax-inclusive, matching the established checkout convention. Product GST components are validated. In-state CGST/SGST and interstate IGST are split correctly, including rounding remainders. Configured tax-inclusive delivery charges have their own explicit tax basis points; a missing delivery tax setting rejects the quote rather than assuming a rate.
- Only configured Indian state/rate combinations and valid six-digit postcodes are serviceable; an optional postcode allowlist further restricts delivery. Test fixtures explicitly use Kerala zero delivery and Tamil Nadu INR50 with a fictional zero delivery-tax rate. **These are test values, not approved commercial shipping terms.**
- Quotes expire after 10 minutes. Order placement re-reads and compares the cart, address, prices, coupon, tax and delivery before accepting the quote. Changing or expiring a quote produces a review/re-quote response.
- Customer/cart/product/coupon locks, current locking reads and conditional stock decrements run inside retryable database transactions. Orders, item totals, inventory history and snapshots commit or roll back together. One active unpaid reservation per customer prevents a second key reserving the same bag again.
- Online items are reserved for 15 minutes and the bag is retained until verified capture. Failed payment attempts can retry the same provider order while reserved. COD is separately configured and commits its stock/cart immediately, without falsely recording a paid online transaction.
- Cancellation and expiry restore reserved stock exactly once. A capture that races or arrives after release is recorded as paid with `refund_required`; it cannot automatically fulfill released stock. Late-capture refund review remains an operator responsibility, not an invented successful refund.
- New storefront orders cannot be confirmed/shipped/delivered by admin actions before their reservation is committed and online capture verified. Admin rejection of an unpaid reservation releases it safely. Accepted delivery charges cannot be silently changed during fulfillment. The existing order value `ontransist` is preserved while status logs use their valid `ontransit` enum.

## Payments, webhooks and refunds

Payment initiation persists an intent before contacting the fixed Razorpay API host. A unique receipt and provider mapping bind it to the order. Mutating provider calls have no automatic HTTP retries: a lost response becomes `indeterminate`, and receipt-based reconciliation recovers it without another charge/order. A delayed creation response cannot downgrade a previously reconciled capture.

The callback HMAC uses the stored provider order ID and backend secret. Capture verification fetches both payment and order and checks ownership, IDs, INR amount, captured status, paid amount and zero amount due. Authorized or failed attempts are recorded without declaring payment success. Duplicate/out-of-order callbacks and webhooks cannot repeat stock/coupon/cart effects or downgrade captured/refunded payments.

Webhook verification hashes the original raw request body. Unique event IDs plus body hashes prevent replay under another ID; reused IDs with different content are rejected. An event whose provider mapping is not yet available remains retryable. Payment transition evidence is retained separately from sanitized webhook receipts; sensitive raw payloads are not stored unnecessarily.

Operator-only test refunds require a collected refund request, verified captured payment, server-calculated discounted/tax-inclusive purchased amount and remaining refundable budget. Delivery is excluded from this test refund rule. Intent uniqueness prevents duplicate refunds; no unknown/refused provider call is automatically resubmitted. Only a fetched processed refund can mark a request refunded and update full/partial payment refund status. Receipt-bound recovery handles lost refund responses. COD/manual refunds, amounts below the provider minimum and late-capture operational payouts need an approved separate process.

Protocol references: [Razorpay callback verification](https://razorpay.com/docs/payments/payment-gateway/quick-integration/build-integration/), [raw webhook validation](https://razorpay.com/docs/webhooks/validate-test/), [order receipt lookup](https://razorpay.com/docs/api/orders/fetch-all/), [normal refunds](https://razorpay.com/docs/api/refunds/create-normal/). Real merchant/test-provider acceptance remains unverified without credentials.

## Returns, replacements, tracking and admin compatibility

Return eligibility uses the first actual recorded delivered timestamp, never a scheduled delivery date or guessed timestamp. It requires delivery, paid/partially-refunded status, the applicable policy window/type and remaining purchased quantity. New orders snapshot the policy; legacy orders use current published policy and fail closed when delivery evidence is missing. Prices supplied by customers are discarded; proportional values derive from the purchased line total, preserving paise across partial returns.

New storefront return transitions are requested → accepted/rejected → picked_up → collected → verified refunded or real replaced. Duplicate transitions are harmless; skipping review or claiming a refund without provider proof is rejected. Collected replacement requests create one real zero-additional-charge linked order, copy the verified address snapshot and atomically deduct available replacement stock once. They do not fabricate shipment events or restock damaged returns. Legacy orders without a verified address snapshot require a reviewed address before replacement. Replacement-order return policy and replacement delivery terms still need business approval for production.

Existing legacy admin order/return paths remain for records without storefront sidecars. Admin product/order pages and legacy status updates have regression coverage. Stock warnings and order/return notifications are preserved through a durable outbox; cache invalidation avoids stale admin lists. Notification failures remain retryable without rolling back a committed order. Admin broadcasts now use authenticated private channels with minimal payloads; customer names/totals render as text rather than HTML. Event names remain compatible with the updated admin layout; public subscriptions to admin data are intentionally removed.

Carrier inspection found internal `delivery_partners`, assigned tracking references, order status logs and manual delivery follow-ups. No Shiprocket, Delhivery or other external carrier client/webhook integration was found. The storefront displays actual Vanthara records and clearly states that carrier updates are not connected. No external tracking response, URL, delivery event or estimate was invented.
