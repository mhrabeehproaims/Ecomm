## 2. Security and correctness findings

| ID / priority | Evidence and consequence | Required closure |
| --- | --- | --- |
| **R01 · High · invoice privacy** | `routes/web.php:127` exposes `/download-invoice/{filename}` outside authentication. A request without any token returned **200** for a synthetic invoice in an isolated storage directory. Real invoices are stored on the public disk by `OrderController`; packing slips are public-disk files too. Predictable invoice filenames increase exposure. No real invoice/customer file was read during this audit. | Authenticate and authorize document access for the owning customer or permitted admin, store documents privately, and remove/deny public static access. Test anonymous, foreign-customer and permitted-admin requests, including old links and cache headers. Protecting only the download route is insufficient if `/storage/Invoices/` remains accessible. |
| **R02 · High · fulfillment documents** | `resources/views/invoices/pdf.blade.php:200` and `packing_slip.blade.php:3` use the customer's **current default address**, not the accepted order snapshot. Synthetic HTML rendering confirmed this, plus a fixed invoice number `INV0000001`, fixed date `04 Nov 2025` and a fabricated fallback carrier `DELHIVERYSURFACE`. The invoice selects GST columns using the current customer profile state, displays the coupon's nominal value rather than necessarily the actual discount, and omits delivery tax from its tax sum. Correct checkout totals do not fix these templates. | Use order-time recipient/address/billing/tax/discount records throughout invoice, packing slip and shipment/email workflows. Use actual invoice number/date and assigned carrier. Add acceptance cases with a nondefault selected address, later profile edits, percentage coupon and taxable delivery; reconcile invoice and stored quote totals. Obtain approved invoice/tax presentation. |
| **R03 · Critical supplier severity · dependency advisories** | `composer audit --locked --no-dev --format=json` returned **59 advisory records across 15 runtime packages**, including 1 critical, 14 high, 30 medium, 6 low and 8 unrated. These are advisory records, not necessarily 59 distinct vulnerabilities or demonstrated exploit paths. Laravel is v12.26.3. The critical TokenGuard advisory affects that version; this application uses Sanctum/session guards rather than the specifically described standard TokenGuard, so direct exploitability is not established. Frontend runtime npm audit returned zero known advisories. | Triage every record and update/lock compatible patched dependencies, rebuild vendor from the lockfile and rerun regression/security tests. Laravel's vendor advisory lists 12.68.0 as a patched 12.x version; that alone does not resolve the other packages. No package or lockfile was changed by this audit. [Laravel advisory](https://github.com/laravel/framework/security/advisories/GHSA-f9x3-7vq9-cph6). |
| **R04 · High · tracked environment/key** | Git tracks root `.env`, including a nonempty APP_KEY and local debug configuration, in existing history. No Razorpay key variables were present in that file, and real test credentials were not supplied to this acceptance run. The normal storefront env remains ignored. | Exclude runtime env files from future commits/build context, assess who could access history and coordinate replacement of any exposed/reused keys. Preserve the local file. Removing a file from the Git index does not erase history. Do not blindly regenerate a deployed APP_KEY: plan encrypted-data/cookie/legacy-link compatibility and backups. Never reuse the checked-in local key for staging/production. |
| **R05 · High · premature webhook completion** | `PaymentService::webhook()` marks an `order.paid` event processed even when its `reconcile()` returns pending. A fake-provider diagnostic sent the order event before any payment was fetchable, then exposed a captured payment and replayed the same event: replay was ignored and the local order stayed unpaid. Explicit manual reconciliation recovered it. This demonstrates handling of a possible timing condition, not a claim that Razorpay always emits that sequence. | Retain/retry unresolved events and verify convergence without browser callbacks. Add durable pending reconciliation and alerting; do not acknowledge business completion solely because a request returned normally. Test eventual provider visibility, lost callbacks and replay. |
| **R06 · High · refunded lifecycle gap** | PaymentService only verifies/reconciles `captured`, `authorized` and `failed`. A synthetic fetched `refunded` payment produced pending reconciliation and HTTP409 verification. Razorpay documents `refunded` as a real payment state. RefundService does verify mapped refund results, but provider-side refunds, missed refund callbacks and subsequent payment reconciliation are incomplete. | Reconcile captured/refunded amounts and mapped/unmapped refund evidence monotonically, without resubmitting a refund. Cover partial/full/manual provider refunds and delayed payment events after refund. [Provider lifecycle](https://razorpay.com/docs/payments/payments/). |
| **R07 · High · webhook latency/recovery** | Webhooks synchronously call provider APIs with 15-second per-request timeouts; capture verification needs two reads and can dispatch outbox effects after commit. The Next private transport aborts after 12 seconds, so initiation can outlast the caller. Signature verification and database idempotency help, but do not ensure prompt webhook acknowledgement. Only one webhook secret is accepted, complicating retries after rotation. | Persist sufficient sanitized recovery data after raw-body HMAC verification, acknowledge promptly and process/reconcile through durable workers. Measure real-provider timing and define secret-rotation overlap/replay recovery. Do not simply shorten timeouts or retry provider mutations. Razorpay describes a five-second webhook window and retries non-2xx deliveries for 24 hours. [Razorpay guidance](https://razorpay.com/blog/payment-gateway-webhooks-india/), [retry rules](https://razorpay.com/docs/webhooks/best-practices/). |
| **R08 · High · unattended operations absent** | `routes/console.php` defines manual expiry/outbox/reconcile/refund commands but **no schedules**. No monitored worker/scheduler deployment, batch reconciliation or alert destinations are supplied. Pending stock/coupon reservations can remain held without expiry execution. Outbox tries effects synchronously; its lease is five minutes and delivery is at least once. Failed effects store an exception class but no operational alert. | Implement and rehearse supervised processing, periodic expiry/outbox retry, targeted/batch payment reconciliation, backlog/failed-refund/late-capture alerts and operator ownership. An OS scheduler invoking today's empty Laravel schedule would do no useful storefront work. Test restart/crash/overlap behavior and one failing reservation not starving the rest. |
| **R09 · High if COD offered · incomplete collection/cancellation** | COD commits stock/cart immediately but leaves payment unpaid. A delivered COD fixture was return-ineligible, and customer cancellation returned409. No cash-collection/reconciliation transition was found. Paid-order admin rejection also does not constitute a managed refund/restock workflow. | Keep COD disabled until collection evidence, customer cancellation, returns/manual payouts and accounting reconciliation are designed, approved and tested. Agree handling of committed/paid cancellations and late captures; an admin status change alone cannot mean refund success. |
| **R10 · Staging acceptance constraint** | CheckoutAccess only permits local/testing environments and narrowly isolated databases; `APP_ENV=staging` is rejected. Next additionally requires a loopback API and private harness identity. Existing test helpers have fixed fictional shipping/tax values and suppress external mail/log effects. | Do not advertise ordinary hosted staging as payment-ready through env flags alone. Use the restricted acceptance topology below, or separately review a dedicated staging adapter. Never remove production guards or expose the test router/identity/fixtures publicly. |

Other identified gaps: the snapshot lacks a separate recipient/billing identity; profile and password-change UX is incomplete; resetting/changing credentials does not revoke other issued sessions automatically; support/contact/policy pages need approved working details; order history and public catalog operations have unbounded reads/N+1 costs; stable product locators remain missing. The backend wishlist decrypt path can return500 for malformed ciphertext. These need scoped fixes/acceptance according to exposure and release scope. No new exploit or full accessibility/performance certification is asserted.

## 5. Deployment requirements and safe staging plan

**Nothing in this plan was deployed.** A normal `APP_ENV=staging` deployment can test browsing/accounts with checkout disabled. Transactional acceptance needs R10's explicit isolated test topology, not a change to production guards.

1. **Prepare a reviewable release.** Resolve R01–R09, update dependencies with compatibility checks, preserve existing uncommitted fixes, review the complete source diff, commit/tag an immutable candidate and retain rollback artifacts. Do not distribute root env files, vendor snapshots, debug output, test databases or backups in a web document root. New acceptance helpers remain private tooling.
2. **Separate infrastructure and credentials.** Use a new staging DB and generated sample data; no raw production customer copy. Supply unique APP_KEY, session secret, least-privilege DB account, nonproduction object storage, test-only Razorpay secrets, mail sink and private broadcast credentials. Default checkout/COD/sandbox flags stay false. Test flags alone cannot enable this code on a production environment/database.
3. **Provide proper processes.** Laravel needs PHP>=8.2 and required extensions (PDO/MySQL, curl, mbstring, OpenSSL, fileinfo, DOM/XML, etc.), PHP-FPM or equivalent behind a web server rooted at `/public`, writable protected storage/cache, and persistent media/document storage. Next requires Node>=20.9, a persistent Node runtime or compatible managed platform, and server-side BFF support; a static export cannot implement these customer endpoints. Keep origins fixed and reachable during build and runtime. Build Laravel's Vite admin assets too. [Laravel deployment](https://laravel.com/framework/docs/12.x/deployment), [Next hosting](https://nextjs.org/docs/app/guides/self-hosting).
4. **Enforce TLS and request boundaries.** Terminate HTTPS at the trusted proxy; configure forwarded host/proto/client address explicitly, exact STOREFRONT_URL, Secure cookies, host allowlists, body limits and timeouts. Block env/Git/vendor/storage backups and public invoices. Restrict staging access; exempt only authenticated webhook ingress as required. Review CSP/frame/network allowances with the real Razorpay SDK before enforcement. Current headers are useful but are not a complete TLS/proxy/security deployment.
5. **Install from reviewed locks.** Use Composer with no dev dependencies and npm ci in a clean candidate directory. Do not deploy the tracked development vendor directory or .phpunit cache. Do not use the scaffold admin seeder for account provisioning. Rebuild Laravel config/routes/views with intended staging settings, restart long-lived services, and build Next with intended origins. Do not clear normal local/production config during this audit. Cached config can otherwise hide new storefront settings.
6. **Migrate only authorized staging.** Verify DB host/schema and take a tested backup first; review the two additive safeguard/outbox migrations and existing legacy constraints. Run additive migration, never migrate:fresh/seed original data. Validate row counts, indexes/uniqueness, admin compatibility and invoice/return behavior with representative synthetic legacy cases. Fresh SQLite/MySQL migration passes do not prove a populated legacy migration succeeds.
7. **Configure financial operations.** Add explicit scheduler jobs for expiry/outbox and a monitored reconciliation runner; choose cadences, bounds/locking and alert owners. Supervise Laravel queue workers where events/listeners use queues; restart on release and set job timeout below retry_after. Merely running queue:work does not drain this custom outbox, nor does today's empty schedule register tasks. Rehearse worker crash, lease expiry, failure backlog and maintenance handling. [Scheduling](https://laravel.com/framework/docs/12.x/scheduling), [queues](https://laravel.com/framework/docs/12.x/queues).
8. **Set observability and rate limits.** APP_DEBUG=false; redact Authorization/Cookie, keys, signatures and PII; retain correlation/order/event IDs and sanitized exception context. Alert on unpaid provider-paid orders, late capture/refund_required, indeterminate intents, stale reservations, retry backlog, gateway errors and failed jobs/refunds. Current code has no configured alerting/APM. Laravel file limits suit one node; select a dedicated shared Redis limiter for multiple instances, outside model-cache flushing. The Next login map is process-local and not authoritative. BFF currently forwards no trusted client attribution, so many customers share the backend server IP's 60/min auth bucket; design and load-test this without trusting arbitrary headers.
9. **Exercise protected staging.** Run all existing checks plus real-provider acceptance, cross-customer documents, nondefault/snapshot fulfillment, financial reconciliation, populated migration rehearsal and throttled/mobile/browser coverage. Measure peak throughput and webhook latency; unthrottled localhost timing is not a production SLO. Verify real test email/private-channel delivery using safe recipients.
10. **Require separate approval.** Review signed commercial rules, gateway evidence, operational runbooks, security/dependency closure and rollback drill with the owner. Live key support and production activation require a separately reviewed code/deployment change: current test-only guards intentionally prevent it. Do not switch live keys or remove gates as a staging shortcut.

Environment checklist: Laravel `APP_ENV`, `APP_DEBUG=false`, unique `APP_KEY`, `APP_URL`, isolated `DB_*`, cache/session/queue/mail/broadcast settings, dedicated limiter store/path and the STOREFRONT test variables listed in section3/config/storefront.php; Next `LARAVEL_API_ORIGIN`, exact `STOREFRONT_URL`, unique session secret, sandbox false by default and `STOREFRONT_INDEXABLE=false`. Production/test secrets must come from separate secret scopes. Shipping and tax variables require owner-approved values before any commercial release.
